# rust-perf — Four-Lane Code Audit (2026-09-11)

**Repo:** `rust-perf` (crate `cargo-perf`) — a static-analysis CLI/LSP tool that scans Rust
source for performance anti-patterns.
**Generated:** unattended overnight run, 2026-09-11. No source files were modified; this is a
report-only artifact. Four parallel specialist lanes (runtime perf, data/query, redundancy/dead
code, over-engineering) were dispatched, cross-corroborated, and every finding below was
adversarially re-checked against the actual code before being recorded.

## Executive summary

- The tool's own hot path is its weakest spot: for **every file**, all **14 registered rules each
  run a full `visit_file` AST traversal** (14× the necessary walk), and `ImportOracle::from_file`
  is rebuilt **4 separate times** per file. This is the highest-leverage fix — it *is* the analysis loop.
- A macro (`impl_loop_tracking_visitor!`) was written specifically to remove loop-tracking
  boilerplate, but is **never invoked**; the boilerplate it targets is copy-pasted **11 times** across
  5 rule files. One change (use the macro) both deletes the duplication and revives the dead macro.
- `NPlusOneQueryRule` ironically has an N+1-shaped bug: `orm_imported()` re-scans the whole source
  (3× `contains`) on every DB-candidate method call inside loops, instead of once per file.
- Several dead/speculative surfaces confirmed: `get_line` (0 callers), `DatabaseConfig.orm` (parsed,
  never read), `define_rule!` (exported, never used), and the `AnalysisProgress` callback (no real consumer).
- Four subagent claims were **refuted and dropped** on verification (details at the end); this report
  keeps only what a concrete file+line substantiates.

## Cross-corroboration (flagged by ≥2 lanes → elevated)

- **E1 / hoist per-file work** — Lane 1 and Lane 2 independently converged on "work that should be
  computed once per file is repeated per node/per rule." Lane 2 caught it at the leaf (`orm_imported`,
  P1); the main-session analysis caught the structural form (14 walks + 4 oracle rebuilds). Same class.
- **E2 / dead macro + duplication** — Lane 3 flagged the 11× duplicated visitor boilerplate (High) and
  Lane 4 independently flagged the macro as an unused abstraction (Low). They are two ends of the same
  defect: the fix for one is the fix for the other.
- **E3 / `get_line`** — Lane 1 (perf) and Lane 2 (data) both landed on `context.rs:114`. Neither found
  a caller; it is dead, so the O(n) is latent rather than live.

## Fixes that close several findings at once

1. **Build `ImportOracle` once and share it via `AnalysisContext`** (`context.rs:90`). Removes the 4
   per-file rebuilds (E1) and gives `orm_imported` a cached home (P1) in one change. A further step —
   a single dispatching visitor that offers each rule its node instead of 14 independent `visit_file`
   passes — collapses the 14× traversal, but is a larger refactor.
2. **Invoke `impl_loop_tracking_visitor!(@methods)` in the 5 rule files** (E2 + D4). Deletes ~11
   copy-pasted blocks (~240 lines) and turns the dead macro into live, tested code simultaneously.
3. **Hoist the file read + `LineIndex` out of the `code_action` loop** (`lsp/mod.rs:448`, P2): read
   once per request, reuse across all overlapping diagnostics.

## Detail

### E1 — 14× per-file AST traversal + redundant `ImportOracle` rebuilds (High)
`engine/file_analyzer.rs:125-164` iterates every rule and calls `rule.check(&ctx)`. Each rule's
`check` constructs its own `syn` visitor and calls `visitor.visit_file(ctx.ast)` — a complete AST
walk. The registry (`rules/registry.rs:19-41`) holds 14 rules, so each file is walked 14 times:
O(14 × nodes) where O(nodes) suffices. Additionally `ImportOracle::from_file` — itself a full
`file.items` scan — is rebuilt independently by 4 rule visitors (`async_rules.rs:58` and `:611`,
`memory_rules.rs:34` and `:445`), duplicating identical per-file work. For a performance linter this
*is* the request path. (Note: disabled rules **are** correctly short-circuited at `file_analyzer.rs:127`
before `check()`, so this is redundant work among *enabled* rules, not wasted work on disabled ones.)

### P1 — `orm_imported()` full-source scan per method call (Medium)
`database_rules.rs:256-258`: `orm_imported()` runs `src.contains("use diesel")`,
`…("use sqlx")`, `…("use sea_orm")` — three full-source scans. It is called at lines 215 and 218
inside `check_method_call`, which fires for every method call while `in_loop()` is true
(`visit_expr_method_call`, 474-477). A loop body full of method calls therefore re-scans the entire
file repeatedly. The result is invariant per file and should be computed once in `check`.

### P2 — LSP `code_action` re-reads the file inside the diagnostic loop (Medium)
`lsp/mod.rs:435-459`: for each stored diagnostic overlapping the request range that has a fix, the
handler does `std::fs::read_to_string(&stored_diag.file_path)` and `LineIndex::new(&source)`. Both
are loop-invariant for a single request; when several fixable diagnostics sit under the cursor the
same file is read from disk and re-indexed once per diagnostic. Read and index once before the loop.

### E2 — unused macro, 11× duplicated boilerplate (Medium)
`rules/visitor.rs:44-86` defines and `pub use`-exports `impl_loop_tracking_visitor!`, whose whole
purpose (per its doc comment) is to generate the `visit_expr_for_loop` / `visit_expr_while` /
`visit_expr_loop` / `visit_expr` loop-depth-tracking methods. A repo-wide grep finds **no
invocation** — only the definition, doc examples, and re-export. Meanwhile `fn visit_expr_for_loop`
appears 11 times across 5 rule files, each with the same ~30-line hand-written block the macro exists
to replace.

### D1 — dead `DatabaseConfig.orm` config field (Medium)
`config.rs:68-71` defines `DatabaseConfig { orm: Option<String> }`, wired into `Config` at line 21
with `#[serde(default)]` so it is parsed and round-tripped from `cargo-perf.toml`. No code ever reads
`config.database.orm` (the only `.orm` hits are the unrelated `orm_imported()` method). A user who
sets `[database] orm = "diesel"` gets silent no-op behavior — a misleading knob.

### P3 — per-line suppression expansion (Low)
`suppression.rs:178-185`: when an item carries a `#[allow(cargo_perf::…)]` attribute,
`add_item_suppressions` loops `for line in start_line..=end_line` and inserts a map entry plus a
cloned rule-set for every line in the item's span. Bounded to items that actually carry a cargo-perf
allow attribute (rare), so severity is low, but a large annotated `impl`/`mod` scales O(lines).

### E3 — dead `get_line` (Low)
`context.rs:114-116`: `pub fn get_line` uses `self.source.lines().nth(...)` (O(n) from the file
start) and has zero callers in the repo. It defeats the O(log n) `LineIndex` it sits next to, but
because nothing calls it the cost is latent. Remove it, or back it with `LineIndex`.

### D2 / D3 — speculative public surface (Low)
`plugin.rs:401` `define_rule!` is `#[macro_export]`ed but never used (only its own doc example).
`engine/mod.rs:26,65` `AnalysisProgress` + `analyze_with_progress` exist for streaming progress, but
the only caller (`analyze`, line 41) passes `|_| {}` and no CLI/LSP path supplies a real callback.
Both are public API, so they *could* serve external consumers — flagged as speculative, not deletable
without an API decision.

### D4 — allocation-rule duplication (Low)
`allocation_rules.rs` carries three structurally identical no-capacity visitors
(`VecNoCapacityVisitor` ~51, `HashMapNoCapacityVisitor` ~227, `StringNoCapacityVisitor` ~399) and
three near-identical constructors `is_vec_new`/`is_hashmap_new`/`is_string_new` (~166/338/513) that
differ only in the type name matched; `mutex_simple_receiver_name`/`mutex_binding_name` (~971)
duplicate `simple_receiver_name`/`binding_name` in `memory_rules.rs:115,128`. Consolidation is a
maintainability win, same family as E2.

## Dropped on verification (honesty ledger)

These were raised by subagents but could not be substantiated against the code, so they are **not**
counted above:

- *"Rules execute before the config enable-check"* (file_analyzer): **refuted** — `file_analyzer.rs:127`
  checks `rule_severity(...).is_none()` and `continue`s before `rule.check()`.
- *"`extract_comment_suppressions` string-searches each line and needs a precompiled pattern"*:
  **refuted** — it is a single necessary linear pass over the source; `str::find` is already fast.
- *"`RegexInLoopRule` is registered but undefined"*: **refuted** — it is defined at
  `memory_rules.rs:419` and the crate compiles in CI.
- *"`fix/mod.rs` has an unreachable defensive canonicalization branch"*: **unsubstantiated** — could
  not confirm the branch is truly unreachable, so dropped rather than speculate.
- Micro-nits (30-element `ITERATOR_ADAPTERS` linear scan, a couple of `PathBuf` key clones in the LSP
  publish path that are already `cargo-perf-ignore`-annotated): real but not concrete failures.
